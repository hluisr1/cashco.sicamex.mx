Documentación Técnica: Prototipo SICAMEX

Análisis de Arquitectura, Reglas de Negocio y Hoja de Ruta

1. Resumen Ejecutivo

Este documento detalla el funcionamiento interno del prototipo actual de SICAMEX. El sistema es una aplicación web frontend-only (SPA simulada) que utiliza archivos JSON locales como base de datos. Su propósito es validar flujos de negocio logístico sin infraestructura de servidor.

Objetivo del análisis: Identificar limitaciones actuales y definir la arquitectura necesaria para migrar a un sistema de producción robusto con base de datos relacional.

2. Módulos Funcionales

El prototipo se divide en 6 vistas principales interconectadas:

📊 Dashboard
KPIs generales, gráfica de ventas por ruta y resumen de operaciones.
📦 Productos
Catálogo maestro, control de stock y precios unitarios.
👥 Clientes
CRM básico con datos de contacto y asignación de ruta/CEDIS.
🚚 Entregas
Registro de salidas, asignación de productos a clientes y estatus.
↩️ Devoluciones
Gestión de merma, retornos de producto y ajuste de inventario.
📈 Indicadores
Tablas dinámicas de rendimiento y eficiencia por zona.

3. Reglas de Negocio Detectadas

Basado en el análisis del código app.js y la estructura de datos, estas son las lógicas críticas actuales:

ID Regla Lógica Actual Prioridad
RN-01 Integridad de Stock El stock no se descuenta automáticamente al crear una entrega en el prototipo (se asume validación manual). Alta
RN-02 Filtrado por CEDIS Toda la información visualizada debe pertenecer estrictamente al CEDIS seleccionado en el modal inicial. Alta
RN-03 Cálculo de Venta Neta Venta Total = (Suma Entregas) - (Suma Devoluciones). Se calcula en tiempo real en el dashboard. Media

RN-05 Unicidad de Cliente Los clientes se identifican por ID, pero no hay validación de duplicados por email o teléfono en el frontend. Media

4. Diagnóstico Técnico (Estado Actual)

✅ Fortalezas del Prototipo

  • Portabilidad: No requiere instalación de servidores ni bases de datos.
  • Velocidad de Desarrollo: Cambios inmediatos en el JSON reflejan cambios en la UI.
  • Desacople Visual: El CSS está bien separado y es mantenible.
  • UX Ágil: Uso de modales y filtrado dinámico sin recargas de página.

⚠️ Debilidades Críticas

  • Persistencia Falsa: Los datos se reinician al recargar la página (no hay backend).
  • Concurrencia Nula: Dos usuarios no pueden trabajar simultáneamente.
  • Seguridad Inexistente: Cualquier usuario puede editar el JSON local.
  • Consultas Ineficientes: Filtrar grandes volúmenes de datos en JS bloquea el navegador.
  • Integridad Referencial Débil: Borrar un cliente no borra sus entregas asociadas (datos huérfanos).

5. Propuesta de Esquema Relacional (Futuro)

Para evolucionar a producción, se propone reemplazar el archivo database.json por una base de datos SQL (PostgreSQL/MySQL). Esto garantiza integridad, transacciones y seguridad.

Modelo Entidad-Relación Propuesto

-- 1. TABLA MAESTRA: CEDIS (Almacenes) CREATE TABLE cedis ( id INT PRIMARY KEY, nombre VARCHAR(100), ubicacion VARCHAR(255), activo BOOLEAN DEFAULT TRUE ); -- 2. TABLA MAESTRA: PRODUCTOS CREATE TABLE productos ( id INT PRIMARY KEY, sku VARCHAR(50) UNIQUE, nombre VARCHAR(150), precio_unitario DECIMAL(10,2), stock_actual INT, cedis_id INT REFERENCES cedis(id) -- Stock por almacén ); -- 3. TABLA MAESTRA: CLIENTES CREATE TABLE clientes ( id INT PRIMARY KEY, nombre VARCHAR(150), rfc_nit VARCHAR(20), direccion TEXT, ruta_asignada VARCHAR(50), cedis_id INT REFERENCES cedis(id) ); -- 4. TRANSACCIONAL: ENTREGAS (Cabecera) CREATE TABLE entregas ( id INT PRIMARY KEY, cliente_id INT REFERENCES clientes(id), fecha_salida TIMESTAMP, fecha_entrega TIMESTAMP, estado ENUM('pendiente', 'en_ruta', 'entregado', 'devuelto'), total_venta DECIMAL(10,2) ); -- 5. TRANSACCIONAL: DETALLE_ENTREGA (Productos por entrega) CREATE TABLE detalle_entrega ( id INT PRIMARY KEY, entrega_id INT REFERENCES entregas(id), producto_id INT REFERENCES productos(id), cantidad INT, subtotal DECIMAL(10,2) ); -- 6. TRANSACCIONAL: DEVOLUCIONES CREATE TABLE devoluciones ( id INT PRIMARY KEY, entrega_id INT REFERENCES entregas(id), motivo TEXT, fecha_devolucion TIMESTAMP, cantidad_devuelta INT );

Beneficios de este esquema:

  • Integridad: No se puede crear una entrega para un cliente que no existe (Foreign Keys).
  • Historial: Se mantiene el registro exacto de qué productos iban en cada entrega.
  • Escalabilidad: Soporta millones de registros sin lentitud.
